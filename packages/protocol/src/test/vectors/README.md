# Test vectors

**Never regenerate anything in this directory.**

A vector exists to prove that code written later still reads bytes written
earlier. One regenerated by the code it is meant to check proves only that the
code agrees with itself — which is exactly the failure this directory exists to
prevent, and the reason the envelope suite could not catch a changed derivation
before these files existed: `fixture()` generates fresh keypairs on every call
and `sealTeamBody` draws a fresh content key per message, so every run sealed
and opened an envelope that was five milliseconds old.

## `team-chat-v1.json`

One AES-GCM team-chat envelope, version byte 1, sealed by `sealTeamBody` as it
stood at commit `a0d6a67` — the last commit before the direct-message envelope
scheme was added. Two exported P-256 keypairs in the same JWK serialisation
`Identity.export()` produces and `apps/web/src/net/identity.ts` persists, a
fixed game id, and the plaintext it should open to.

The game id is a literal rather than a sealed genesis on purpose: a vector that
re-derived its id would break the day `makeGenesis` gains a default field, and
would then be "fixed" by regenerating it, which is how a compatibility test
quietly becomes a tautology.

**Why it matters beyond the suite.** `ArchivedGame.messages` holds every
`SignedMessage` exactly as it crossed the wire, so archives on disk already
contain v1 bodies. `openTeamBody` is the only thing that will ever read those
again.
